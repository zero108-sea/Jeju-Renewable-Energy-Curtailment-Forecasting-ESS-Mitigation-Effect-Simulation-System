## 02. 항목별 결정 내용

### 1) WeatherHour null 처리 — 타입은 nullable이지만 조건부 필수입니다

**혼란을 드린 부분을 먼저 인정합니다.** 스키마가 `Optional[float] = None`이라 "널을 보내도 된다"로
읽히는 게 당연합니다. 실제로는 **`energy_type`에 따라 필수가 갈립니다.**

| energy_type | 24시간 모두 필요 | 보내도 되고 안 보내도 되는 것 |
|---|---|---|
| `"solar"` | `solar_rad`, `temp`, `cloud` | `wind_speed` |
| `"wind"` | `wind_speed` | `solar_rad`, `temp`, `cloud` |

Optional로 둔 이유는 v1.0 2)번에서 합의한 **단일 DTO 원칙** 때문입니다. 에너지원별로 DTO를
나누면 클래스가 두 벌이 되므로, 필드는 하나로 두고 검증만 `energy_type`으로 분기합니다.

**한 시간이라도 null이면 422입니다.** 조용히 0으로 대체하지 않습니다 — 풍속 null을 0으로 바꾸면
'제어 없음'으로 오예측합니다(이 동작을 실제로 겪어 고쳤습니다).

```json
// 요청: wind인데 13시부터 wind_speed가 null
{ "error_code": "MISSING_REQUIRED_FIELD",
  "message": "wind 예측에는 wind_speed가 모든 시간에 필요합니다 (누락: 13시.wind_speed, 14시.wind_speed, … 외 7건)" }
```

누락 위치를 `<시>시.<필드>` 형태로 **최대 5건까지** 메시지에 담습니다. 그대로 릴레이하시면
어느 시간이 비었는지 사용자가 바로 압니다.

> **풍력 요청에 태양광 기상값을 함께 보내는 것을 권장합니다.** 필수는 아니지만, 보내면 계통 전체
> 침투율 모델로 자동 전환되어 성능이 올라갑니다(PR-AUC 0.743 → 0.831). 어느 모델이 쓰였는지는
> 응답의 `model_used`로 확인할 수 있습니다.

### 2) region 값 형식 — 제약 없습니다. 그대로 돌려드립니다

**모델이 이 값을 쓰지 않습니다.** 제주 전역 단일 모델이라 지역으로 분기하지 않습니다.
`"제주"`, `"남원읍"`, `"제주특별자치도 서귀포시 남원읍"` 모두 **같은 예측**을 냅니다.

- 형식: 자유 문자열, 1~100자
- 용도: 응답에 그대로 echo. 화면 표시에 쓸 문자열을 보내시면 됩니다
- 거부: 빈 문자열, 공백만 있는 값, 100자 초과

빈 값을 막은 이유는 그대로 echo하면 **화면에 빈칸이 뜨기 때문**입니다. v1.0까지는 통과했습니다.

```json
{ "error_code": "MISSING_REQUIRED_FIELD", "message": "region은 비어 있을 수 없습니다" }
```

> 지역별 모델은 로드맵에 있지만 현재 데이터로는 불가능합니다 — 출력제어 실적이 제주 전체 단위로만
> 공개되어 지역별 라벨이 없습니다.

### 3) 422 에러 형식 — `{error_code, message}` 고정입니다

모든 4xx 응답이 같은 모양입니다.

```json
{ "error_code": "INVALID_HOUR_SET", "message": "weather 배열은 정확히 24개여야 합니다" }
```

| error_code | 발생 조건 |
|---|---|
| `INVALID_HOUR_SET` | weather가 24개가 아니거나, 1~24시 각 1회가 아님(중복·누락) / `demand_forecast_mw` 길이 ≠ 24 |
| `MISSING_REQUIRED_FIELD` | 발전원별 필수 기상값이 null / region이 빈 값 |
| `INVALID_SOC_RANGE` | `/ess/simulate`에서 `soc_min >= soc_max` |
| `INVALID_ENERGY_CAPACITY` | `/ess/simulate`에서 `energy_capacity_mwh <= 0` |
| `LENGTH_MISMATCH` | `/ess/simulate`에서 `hour_of_day` 길이 ≠ `hourly_curtailment_mwh` |
| `VALIDATION_ERROR` | 그 밖의 형식 오류(타입 불일치, 필수 필드 누락 등) |

`VALIDATION_ERROR`는 pydantic이 잡은 형식 오류이고, **메시지 끝에 `(위치: <필드경로>)`를 붙입니다.**

```json
{ "error_code": "VALIDATION_ERROR", "message": "Field required (위치: weather)" }
```

위치 표기는 v1.1에서 추가했습니다 — 그 전에는 `"Field required"`만 와서 어느 필드인지
알 수 없었습니다.

**세 조치 모두 필요했던 것이 확인됐습니다.**

### 한 곳이 어긋납니다 — `WeatherHour.temp`

`temp`만 **`double` 프리미티브**이고 나머지 셋(`solar_rad`, `cloud`, `wind_speed`)은 `Double`
래퍼입니다. 프리미티브는 null을 표현할 수 없어 **Jackson이 누락·null을 0.0으로 채웁니다.**

| Backend가 보낸 값 | AI 서버 응답 | 태양광 24시간 발전량 합 |
|---|---|---|
| `temp: 15.0` (정상) | 200 | 1,032.6 MWh |
| `temp: 0.0` (Jackson 기본값) | **200** | **1,588.7 MWh** |
| `temp: null` (`Double`이었다면) | **422 MISSING_REQUIRED_FIELD** | — |

**발전량이 54% 부풀려진 채 200이 나옵니다.** 01장 1)번에서 "조용히 0으로 대체하지 않는다"고
적은 실패 방식이 Backend 쪽에서 되살아납니다 — 그쪽에서 이미 0으로 바꿔 보내므로 AI 서버의
422 검증이 발동하지 않습니다.

**요청: `double temp` → `Double temp`.** 한 글자입니다.

그리고 주석의 `"기온(℃) - 공통 필수"`도 정확하지 않습니다.

- `energy_type="solar"` → **필수**
- `energy_type="wind"` (풍력 기상값만 보낼 때) → 쓰이지 않음
- `energy_type="wind"` + 태양광 기상값 동봉 → `crossp` 경로로 전환되며 **쓰입니다**

세 번째가 권장 사양이라(01장 1)번 인용), 실질적으로는 두 경우 모두 보내주시는 게 맞습니다.

## 06. 값 범위 검증 추가 (2026-09-30)

05장에서 "연동 전에 넣을지 의견 부탁드립니다"라고 했는데, **물어볼 사안이 아니었습니다.**
기상청 예보에서 음수 일사량이나 초속 500m 바람이 나올 일이 없으므로 **정상 트래픽은 하나도
막히지 않습니다.** 새로 거부되는 것은 이미 쓰레기인 값뿐입니다. 그래서 바로 넣었습니다.

### 넣기 전에는 이랬습니다

| 보낸 값 | 응답 | 태양광 발전량 합 |
|---|---|---|
| 정상 | 200 | 1,032.6 MWh |
| `solar_rad: -1` | **200** | 715.4 MWh |
| `solar_rad: 999` | **200** | 4,303.3 MWh |
| `wind_speed: 500` | **200** | 1,581.9 MWh |

드리프트 경고가 `note`에 실리긴 했지만 **HTTP는 200**이라, `note`를 파싱하지 않으면 쓰레기
예측이 DB와 화면까지 갑니다.

### 허용 범위

상한은 **제주 ASOS 184 실측(2021~2023)보다 넉넉히** 두고 물리 한계만 지켰습니다 — 예보가 실측
범위를 조금 넘는 것은 정상이므로 그것까지 막으면 안 됩니다.

| 필드 | 실측 범위 | 허용 범위 | 근거 |
|---|---|---|---|
| `solar_rad` | 0.0 ~ 3.9 | **0 ~ 6** | 음수 불가 |
| `temp` | −3.1 ~ 37.0 | **−30 ~ 50** | |
| `cloud` | 0.0 ~ 10.0 | **0 ~ 10** | 기상청 전운량 정의 |
| `wind_speed` | 0.0 ~ 13.7 | **0 ~ 60** | 음수 불가, 태풍 최대풍속 여유 |
| `demand_forecast_mw` | 378 ~ 1,104 | **0 초과** | |

`/ess/simulate`도 함께 막았습니다.

| 필드 | 규칙 | 이전 동작 |
|---|---|---|
| `hourly_curtailment_mwh` | 빈 배열 불가, 각 값 0 이상 | 빈 배열이 200/흡수율 0.0 |
| `rated_power_mw` | 0 초과 | `-10`이 **흡수율 −1.0**을 반환 |

### Backend 영향

**새 에러코드 `OUT_OF_RANGE` 하나가 늘었습니다.** 01장 3)번 표에 추가해 읽어주세요.

| error_code | 발생 조건 |
|---|---|
| `OUT_OF_RANGE` | `demand_forecast_mw`에 0 이하 / `hourly_curtailment_mwh`에 음수 |
| `VALIDATION_ERROR` | 기상값이 허용 범위 밖 (pydantic이 잡음) |

기상값 범위 위반은 `VALIDATION_ERROR`로 오고 **메시지에 위치가 붙습니다.**

```json
{ "error_code": "VALIDATION_ERROR",
  "message": "Input should be greater than or equal to 0 (위치: weather.0.solar_rad)" }
```

즉 **Backend가 처리할 코드는 늘지 않습니다** — 이미 두 코드를 릴레이하고 있으므로 그대로 두면
됩니다. 다만 `OUT_OF_RANGE`를 도메인 코드 목록에 넣어두시면 로그에서 구분됩니다.

`tests/test_api_contract.py`에 22종을 추가해 고정했습니다(총 49종). **범위 밖은 422, 실측 범위
안은 200**을 양방향으로 검증하므로, 상한을 잘못 조여 정상 예보를 막는 일도 잡힙니다.

## 07. AI 서버 연동 테스트 결과 (2026-10-01)

**Spring Boot와 AI 서버를 실제로 함께 띄워 전체 경로를 호출했습니다.** 05장은 Java DTO 모양을
흉내낸 JSON을 AI 서버에 직접 보낸 것이었고, 이번에는 Backend를 실제로 거칩니다.

```
AI 서버   .venv/bin/python -m uvicorn app.main:app --port 8000
Backend   mvn spring-boot:run -Dspring-boot.run.profiles=localtest
```

### 실행을 위해 추가한 것 — H2 프로파일

PostgreSQL이 설치돼 있지 않아 Backend를 띄울 수 없었습니다. **기본 프로파일은 건드리지 않고**
인메모리 H2 프로파일을 더했습니다(`pom.xml`에 H2 `runtime` 의존성, `application-localtest.yml`).
운영·개발은 그대로 PostgreSQL을 씁니다. DB 설치 없이 연동을 확인할 수 있으니 필요하실 때 쓰세요.

### 결과

| # | 검증 | 결과 |
|---|---|---|
| ① | `POST /api/regions` 지역 등록 | ✅ |
| ② | **`POST /api/predictions` — Backend → AI → DB 전체 경로** | ✅ **24건 저장** |
| ③ | `GET /api/predictions/{regionId}` 조회 | ❌ **500** (아래) |
| ④ | AI 서버 검증 에러 릴레이 | ✅ |

**② 전체 경로가 실제로 돕니다.**

```
[1시]  targetHour=2026-10-02T01:00:00  prob=0.006  gen=148.39  curtailmentMwh=0.19
       modelUsed=classifier_wind_demand_crossp_lr_calibrated_sigmoid
       threshold=0.01  reliable=false  note 414자
[24시] targetHour=2026-10-03T00:00:00   ← 24시 → 다음날 00:00 변환 정상
```

`model_used`·`operational_threshold`·`note` 모두 DB까지 온전히 들어갑니다. **note 414자가
TEXT 컬럼에 저장되는 것도 실제로 확인**됐습니다.

**④ 06장에서 넣은 값 범위 검증이 Backend를 그대로 통과합니다.**

```
음수 일사량 요청 → HTTP 422
{"error_code":"VALIDATION_ERROR",
 "message":"Input should be greater than or equal to 0 (위치: weather.0.solar_rad)"}
```

AI 서버 → Backend → 클라이언트까지 **에러코드와 위치 정보가 손실 없이 전달**됩니다.
`GlobalExceptionHandler`의 4xx 릴레이가 의도대로 동작합니다.

### ③ 버그 — `GET /api/predictions/{regionId}`가 500입니다

```
HttpMessageConversionException: Type definition error:
  [simple type, class org.hibernate.proxy.pojo.bytebuddy.ByteBuddyInterceptor]

No serializer found for class ByteBuddyInterceptor
  (through reference chain:
   ArrayList[0] -> CurtailmentPrediction["region"]
                -> Region$HibernateProxy["hibernateLazyInitializer"])
```

**JPA 엔티티를 API 응답으로 직접 반환해서** 생긴 문제입니다. 조회 시 `Region`이 지연 로딩
프록시로 들어오는데 Jackson이 그 내부 필드(`hibernateLazyInitializer`)를 직렬화하려다 실패합니다.

**`POST`는 왜 되는가** — 방금 저장한 객체라 프록시가 아닌 실제 인스턴스입니다. 그래서 저장
경로는 멀쩡하고 **조회만 깨집니다.** 화면에서 저장된 예측을 불러오는 순간 드러납니다.

해법은 둘입니다.

| 방법 | 설명 |
|---|---|
| **응답 DTO 분리** (권장) | `CurtailmentPrediction` → 응답 전용 DTO로 변환해 반환. 엔티티 변경이 API 계약을 깨지 않게 되는 부수 효과도 있습니다 |
| 어노테이션 | 엔티티에 `@JsonIgnoreProperties({"hibernateLazyInitializer", "handler"})`. 한 줄이지만 엔티티를 그대로 노출하는 구조는 남습니다 |

Backend 영역이라 저희 쪽에서 고치지 않았습니다. **시연에서 조회 화면을 쓸 계획이면 그 전에
필요합니다.**

### 부수 확인

- `Region`은 `energySource`가 NOT NULL입니다 — 등록 시 `{"name":"남원읍","energySource":"WIND"}`
  형태여야 합니다. `name`만 보내면 `REGION_ID` NOT NULL 위반으로 저장이 실패합니다
- 로컬 기본 `java`가 15라 `JAVA_HOME`을 21로 지정해야 빌드됩니다(CI는 temurin 21이라 무관)
- 05장에서 요청드린 **`WeatherHour.temp` → `Double`은 아직 그대로**입니다

## 08. `/health` 개선 + `OUT_OF_RANGE` 코드 정리 (2026-10-06)

이성헌 님이 지적하신 두 가지입니다.

### `/health`가 모델 적재 여부를 보고합니다

지적대로 상수 `{"status":"ok"}`는 헬스체크 역할을 못 했습니다. **기동 시 미리 로드하는 방식**으로
바꿨습니다(제안하신 두 방법 중 첫 번째).

```json
// 정상
{"status":"ok", "loaded":9, "missing":[], "ready":true}

// 아티팩트 누락
{"status":"degraded", "loaded":0, "ready":false,
 "missing":["converter_solar","converter_wind","classifier_solar_calibrated_sigmoid", ...]}
```

| 항목 | 내용 |
|---|---|
| `ready` | 예측에 필요한 아티팩트가 모두 있는지. **Backend는 이 값만 보면 됩니다** |
| `status` | `ready`에 연동 — `ok` / `degraded` |
| `missing` | 없는 아티팩트 이름. 운영에서 무엇을 배포해야 하는지 바로 보입니다 |
| `loaded` | 적재된 개수 |

**부수 효과로 첫 요청 지연이 사라졌습니다** — 약 800ms → 159ms. 기동 시 한 번 읽어두기 때문입니다.

**아티팩트가 없어도 서버는 뜹니다.** 기동을 막으면 원인을 볼 창구가 없어지므로, 대신 `ready=false`로
알립니다. `/health` 자체는 50회 평균 0.48ms로 가볍습니다.

### `OUT_OF_RANGE` — 06장에 이미 넣었습니다

확정서 06장 「Backend 영향」 표에 들어가 있습니다. 다시 적으면:

| error_code | 발생 조건 |
|---|---|
| `OUT_OF_RANGE` | `demand_forecast_mw`에 0 이하 / `hourly_curtailment_mwh`에 음수 |

기상값 범위 위반은 **`VALIDATION_ERROR`로 오고 메시지에 위치가 붙습니다**(`위치: weather.0.solar_rad`).
즉 Backend가 새로 분기할 코드는 없고, 도메인 코드 목록에 `OUT_OF_RANGE` 한 줄만 추가하시면
로그에서 구분됩니다.

## 10. 응답에 모델 학습시각 추가 + 요청 로깅 (2026-10-06)

### `model_trained_at` — 추가 필드 하나입니다

`model_used`는 **경로 이름**이라 재학습해도 바뀌지 않습니다. 그래서 예측 결과를 DB에 쌓아둔 뒤
"이 수치는 어느 모델이 낸 것인가"를 되물으면 답할 방법이 없었습니다.

```json
{
  "model_used": "classifier_wind_demand_crossp_lr_calibrated_sigmoid",
  "model_trained_at": "2026-09-27T06:22:32+00:00",
  ...
}
```

**추가만 되는 변경이라 기존 코드는 그대로 동작합니다.** 다만 `CurtailmentPrediction`에 컬럼을
하나 더 두시면 좋겠습니다 — 재학습 전후 예측이 DB에 섞이는 순간, 이 값이 유일한 구분 단서입니다.

| 필드 | 타입 | 비고 |
|---|---|---|
| `model_trained_at` | `String` (nullable) | ISO 8601, UTC. 아티팩트 메타의 `trained_at`과 동일 |

### 요청 로깅

운영 중 무엇이 있었는지 남지 않아 사후 추적이 불가능했습니다. 한 줄 로깅을 넣었습니다.

```
2026-10-06 12:47:29 INFO  ai_server warmup loaded=9 ready=True missing=[]
2026-10-06 12:47:29 INFO  ai_server POST /predict -> 200 (124ms)
2026-10-06 12:47:29 WARN  ai_server POST /predict -> 422 (1ms)
```

4xx 이상은 `WARNING`으로 올라갑니다. **요청 본문은 남기지 않습니다** — weather 24개가 매 요청
로그에 쌓이면 읽을 수 없게 되고, 기상값이라도 입력 전체를 로그에 남기는 것은 좋은 습관이 아닙니다.
