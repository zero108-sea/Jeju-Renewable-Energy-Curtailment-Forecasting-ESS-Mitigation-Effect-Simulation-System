조만간 정정하겠습니다.

### 제가 계속 맡겠습니다

| 영역 | 이유 |
|---|---|
| 등급 밴드 로직 (일내 순위 + 경로별 바닥값) | 모델 쪽 결정과 직결 |
| 모델 경로 판정 | 응답의 `model_used`에서 역산한다. 화면에서 조건을 재조합하면 서버의 자동 전환(태양광 기상값이 오면 `crossp`로 바뀜)과 어긋나 **다른 경로의 바닥값이 조용히 적용된다** |
| 검증 리포트 탭 | 산출물 CSV 구조와 직결 |

### 이어받아 주시면 좋을 것

- **Backend REST 경유 전환** — 지금은 서비스 함수를 in-process로 직접 부릅니다. 시연 중
  FastAPI가 죽으면 복구할 시간이 없어 그렇게 뒀는데, 결과적으로 **Java Backend ↔ AI 서버
  아키텍처를 화면으로 증명하지 못합니다.** 소개서 4.1이 REST 분리를 강조하는데 대시보드가
  그 경로를 안 씁니다
- **지역 선택** — `region="제주"` 고정입니다. `RegionController`가 있는데 화면엔 없어
  어긋나 보입니다
- **배포** — 로컬 `streamlit run`뿐입니다

### 합의가 필요한 것

REST로 바꾸면 아키텍처는 증명되지만 **장애점이 하나 늘어납니다.**

절충안으로 **"REST 기본 + 실패 시 in-process 폴백"** 을 생각하는데, 그러면 어느 경로로 돌았는지
화면에 표시해야 합니다. 지금 일사량 출처(`kim_l010` / `estimator`)를 표시하는 방식과 같게 하면
일관됩니다. 어떻게 보시는지요?

## 2. `/health`가 상수 응답인 문제

**지적하신 대로였습니다.** 제안하신 두 방법 중 **'기동 시 미리 로드'** 로 고쳤습니다(v1.1 08장).

```json
// 정상
{"status":"ok", "loaded":9, "missing":[], "ready":true}

// 아티팩트 누락
{"status":"degraded", "loaded":0, "ready":false,
 "missing":["converter_solar","converter_wind","classifier_solar_calibrated_sigmoid", ...]}
```

| 필드 | 쓰는 법 |
|---|---|
| `ready` | **Backend는 이 값만 보면 됩니다** |
| `status` | `ready`에 연동 (`ok` / `degraded`) |
| `missing` | 없는 아티팩트 이름. 운영에서 무엇을 배포해야 하는지 바로 보입니다 |

**아티팩트가 없어도 서버는 뜹니다.** 기동을 막으면 원인을 볼 창구가 없어지므로 `ready=false`로
알리는 쪽을 택했습니다.

부수 효과로 **첫 요청 지연이 800ms → 159ms**로 줄었습니다. `/health` 자체는 50회 평균 0.48ms입니다.

## 3. `OUT_OF_RANGE` 추가 여부 · 일정

**네, 추가해 주세요.** 사실 v1.1 06장에 이미 적어뒀는데 눈에 띄지 않았던 것 같습니다 —
제 전달이 부족했습니다. 08장에서 다시 짚었습니다.

| error_code | 발생 조건 |
|---|---|
| `OUT_OF_RANGE` | `demand_forecast_mw`에 0 이하 / `hourly_curtailment_mwh`에 음수 |

기상값 범위 위반(`solar_rad: -1` 등)은 **`VALIDATION_ERROR`로 오고 메시지에 위치가 붙습니다**
(`위치: weather.0.solar_rad`). 즉 **새로 분기할 코드는 없고** 목록에 한 줄만 추가하시면
로그에서 구분됩니다.

### 일정에 대해

10/11 제출까지 하루 여유뿐이라 9일 E2E에서 뭔가 나오면 바로 밀립니다.

다만 **제출물은 작품소개서이고 코드가 아니라서** 9·10일이 밀려도 제출 자체는 위험하지 않습니다.
진행률 표기만 그때 맞추면 됩니다. **실제 마감은 11/11 시연**이고 36일 남았습니다.

가능하시면 **9일을 기다리지 말고 지금 한 번 돌려보시는 걸** 권합니다. 제 쪽은 H2로만 확인했고
운영 DB는 미검증이라, 스키마 제약이나 타입 차이가 있으면 지금 발견하는 게 낫습니다.

## 추가사항

### ① 올려주신 두 건 모두 검증했습니다

`b62802e`를 실제로 띄워 재확인했습니다(v1.1 09장).

| 검증 | 이전 | 지금 |
|---|---|---|
| `POST /api/predictions` | ✅ | ✅ 24건 저장 |
| `GET /api/predictions/{id}` | ❌ 500 | ✅ **200** |
| `temp: null` | ❌ 200 통과 | ✅ **422** |
| `temp` 필드 누락 | ❌ 200 통과 | ✅ **422** |

응답 DTO 분리가 정확합니다. `regionName`을 문자열로 평탄화해 프록시가 응답에 섞이지 않고,
엔티티 변경이 API 계약을 깨지 않는 효과까지 그대로 얻었습니다.
**05·07장 Backend 항목은 모두 닫혔습니다.**

### ② 응답에 `model_trained_at`이 추가됐습니다

```json
"model_used": "classifier_wind_demand_crossp_lr_calibrated_sigmoid",
"model_trained_at": "2026-09-27T06:22:32+00:00"
```

**추가만 되는 변경이라 기존 코드는 그대로 동작합니다.** 다만 `model_used`는 경로 이름이라
재학습해도 바뀌지 않습니다. **재학습 전후 예측이 DB에 섞이는 순간 이 값이 유일한 구분 단서**입니다.

### ③ 신제도 구간에서 `note`가 길어집니다

`target_date`가 2024-06 이후면 `expected_curtailment_mwh`의 근거가 약하다는 경고가 `note`에
추가로 붙습니다(**414자 → 583자**). TEXT 컬럼으로 바꿔두신 게 여기서도 필요했습니다.

그 구간에서 확률의 **크기**가 검증되지 않았기 때문입니다(2025년 Brier 스킬스코어 −0.234 —
상수 예측기보다 나쁨). 값을 null로 바꾸면 이미 쓰고 계신 필드 계약이 깨지므로 `note`로만 알립니다.

### ④ 요청 로깅이 들어갔습니다

```
INFO  ai_server POST /predict -> 200 (124ms)
WARN  ai_server POST /predict -> 422 (1ms)
```

4xx 이상은 `WARNING`입니다. 연동 중 문제가 생기면 AI 서버 쪽 로그를 보시면 됩니다.
